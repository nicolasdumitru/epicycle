# Design decisions

Short records of choices that are non-obvious or expensive to reverse.
Newest decisions are appended at the end of each section.

## Stack

- **Tauri 2** shell. The domain logic lives in Rust crates that don't depend on Tauri.
- **Frontend: SvelteKit + Svelte 5 + TypeScript**, built as a static single-page app
  (`adapter-static`, `ssr = false`). SvelteKit is used for routing, which mobile back
  navigation needs. TypeScript types for domain data will be generated from the Rust
  types with `ts-rs`, so Rust remains the single source of truth.
- **Charts are hand-written SVG** until a chart library clearly earns its place.
- **The monthly chart** (2026-11-03) puts what is paid in each month (columns,
  scheduled cash flow) and the monthly equivalent of what is active (a line,
  commitment) on one axis, in the dashboard's currency. It covers six months
  back to six ahead; past months are estimates, drawn lighter and labelled as
  such. Commitment is taken on each month's first day (today, for the current
  month), and each month is converted with the rates nearest its date. Colours
  are the dataviz reference palette's first two slots, validated against the
  app's light and dark surfaces. Every value is also in a table view.
- **pnpm**, with every version pinned exactly and `minimumReleaseAge` set to 7 days
  (`ui/pnpm-workspace.yaml`). An urgent security fix can be exempted via
  `minimumReleaseAgeExclude`.
- **TypeScript 6.x.** SvelteKit 3 and svelte-check don't support TypeScript 7 yet.
- **Storage: SQLite through `sqlx`**, chosen for compile-time checked queries. The
  offline query metadata (`.sqlx/`) is committed so that CI and the Nix build need
  no live database (`SQLX_OFFLINE=true`).
- **Layout:** Rust crates live in `crates/` and the frontend in `ui/`. The root
  `Cargo.toml` is a workspace manifest only. There are two crates: `crates/core`
  (pure domain logic; the crate boundary guarantees it can't use Tauri or SQL) and
  `crates/app` (Tauri commands plus storage). Storage is a module of the app crate
  until a second program, such as a CLI, needs the database.
- **App identifier: `io.github.nicolasdumitru.epicycle`.** It determines the data
  directory on every platform and the iOS bundle ID, so it must not change.

## Packaging

- **NixOS: a flake package** (`nix/package.nix`, 2026-11-03), built like the
  Tauri apps in nixpkgs: `rustPlatform.buildRustPackage` with the `cargo-tauri`
  hook, and the frontend's pnpm dependencies fetched by `fetchPnpmDeps` (a
  fixed-output hash to update when `ui/pnpm-lock.yaml` changes). The source is
  limited to what the build reads, so documentation changes don't rebuild it.
  Tests aren't rerun in the package build; CI runs them.

- **Releases are GitHub Releases, made by pushing a version tag** (2026-11-04).
  `.github/workflows/release.yml` checks that the tag matches the version in
  `Cargo.toml` and `tauri.conf.json`, calls the Android and Windows workflows
  (which double as reusable workflows), and publishes their files with
  `gh release create`. Release assets download without a GitHub account,
  unlike run artifacts. A release APK must be signed: the Android workflow
  fails rather than publish an unsigned one. Plain pushes of tags don't also
  run the per-branch workflows.

## Platforms

- Validation order: **NixOS desktop, then iOS**, then iPadOS, Windows, macOS, Android.
- iOS builds need macOS with Xcode, which isn't available yet; a remote macOS build
  machine will be used.
- **Android (2026-11-03): a second dev shell, `nix develop .#android`**, with
  everything in the default shell plus the Android SDK, NDK, JDK 25 (the current
  LTS; the Android Gradle plugin needs 17 or newer) and Rust's
  Android targets. The default shell stays lean. Both are built from one shared
  package list so they can't drift apart.
  - The SDK is pinned in `flake.nix` and lives in the read-only Nix store, so
    Gradle can't download missing pieces. The app compiles against SDK 37 with
    build-tools 37 (set in `crates/app/gen/android/app/build.gradle.kts`);
    Tauri's own Android library still wants SDK 36 and build-tools 36, so the
    shell has both.
  - Gradle's own aapt2 is a generic Linux binary that doesn't run on NixOS; the
    shell points Gradle at the SDK's (`GRADLE_OPTS`).
  - The Android project (`crates/app/gen/android`) is generated by
    `cargo tauri android init` and committed, as Tauri intends: it now has our
    changes (build-tools version, release signing).
  - **Release builds are signed with our own key**, created with
    `just android-keystore` and kept by the user; CI gets it from GitHub
    secrets. Every release build then installs over the last. Local debug
    builds use the machine's Android debug key, so they don't install over
    release builds or the other way round.
  - APKs target 64-bit ARM only, which covers current phones; other targets
    can be added to the build command if needed.
  - **The emulator is a separate flake package** (`nix run .#android-emulator`,
    a Pixel 10 with Android 16), not part of the Android shell, so CI doesn't
    download the system image. It is a small launcher of our own
    (`nix/android_emulator.py`) rather than nixpkgs' `emulateApp`, which pins
    command-line tools too old to know phones after the Pixel 6. It was briefly
    removed in favour of Android Studio and brought back (2026-11-04).
  - **The emulator starts without Vulkan passthrough** (`-feature -Vulkan`):
    with it, Android's WebView hung initialising Vulkan on the host GPU, and
    the app froze on a white screen. OpenGL still uses the GPU. If graphics
    misbehave anyway, `just android-emulator -gpu swiftshader_indirect`
    renders in software.
  - **Safe areas on Android are handled natively** (2026-11-03): the app draws
    edge to edge, but Android's WebView reports 0 for CSS
    `env(safe-area-inset-*)`. `MainActivity` pads the content by the status
    bar, gesture bar, camera cutout and keyboard instead, and the window
    background matches the page's, so the bars sit on the app's colour in light
    and dark mode. iOS uses the CSS insets, which WebKit reports.
  - **The database is registered before start-up opens it** (`DbHandle`):
    on Android the web view can call commands while start-up is still waiting
    for the data folder from the Java side, and they used to fail with "state
    not managed". Commands now wait until it is open.

## Domain

### Money
- Amounts are integer minor units (`i64`) paired with an ISO 4217 currency. Amounts
  in different currencies are never added without an explicit conversion.
- Exchange rates and derived values (such as the monthly equivalent of a weekly
  price) are exact decimals. They are rounded half-to-even only for display.

### Recurrence
Billing rules are an algebraic data type. Calendar rules and duration rules are kept
separate:

| Rule | Meaning |
|---|---|
| `Days { every }` | Every *n* days. A pure duration. |
| `Weeks { every }` | Every *n* weeks, on the anchor's weekday. |
| `Months { every, day }` | Every *n* months on a fixed day of the month (1–31). |
| `Years { every, month, day }` | Every *n* years on a fixed date. |

- **Day 31 means "the last day of the month".** Clamping makes it fall on the last
  day of every month, so a separate "last day" option would be a second way of
  writing the same rule.
- **Weekly rules don't store a weekday.** It always equals the anchor's weekday,
  and storing it twice would allow the two to disagree.

- Each rule comes with an **anchor**: one real payment date that fixes the phase,
  i.e. which month or week the "every *n*" counts from. A smart constructor rejects
  an anchor that doesn't satisfy the rule.
- The *k*-th payment is computed directly as `anchor + k × interval`, never from the
  previous payment, so dates can't drift. A day that doesn't exist in a month is
  clamped to that month's last day: day 31 falls on Feb 28/29, then on Mar 31 again.
  Feb 29 falls on Feb 28 in years that aren't leap years.
- The billing day is stored explicitly rather than read from the anchor date.
  Otherwise "the 28th" and "the last day" would be indistinguishable when the
  anchor is Feb 28.
- The next payment date is always derived, never stored.

### Normalising to monthly and annual equivalents
- Month and year rules convert exactly: amount *a* every *n* months is `12a/n`
  per year.
- Day and week rules use the **mean Gregorian year, 365.2425 days** (52.1775 weeks
  per year, 30.436875 days per month). A commitment is a long-run rate, so it needs
  an average year. 52 weeks per year would understate weekly costs by about 0.3%.
- Scheduled cash flow uses no averages: it counts the actual payment dates in a
  period, so a year with 53 weekly payments shows 53.

### Subscriptions: plan history and status history
- **A subscription keeps a history of plans, not only of prices.** A plan is a
  billing schedule plus an amount, in effect from a date until the next plan.
  Switching from monthly to yearly billing, or moving the billing day after a
  pause, is a new plan. A price change is a new plan with the same schedule.
  Without this, editing a schedule would silently rewrite every past estimated
  payment.
- **The first plan's date is the subscription's start.** No payments are counted
  before it.
- **Status changes take effect on their date.** A subscription is active until the
  first change. A payment that falls on the day a pause or cancellation takes
  effect is not counted, and one on the day it becomes active again is.
- **A subscription's currency is fixed.** Changing currency means creating a new
  subscription.
- Every period is half-open, `[from, to)`, so consecutive periods never count a
  payment twice.
- **A free period is a plan with amount 0** (2026-11-03): a free trial, or time
  already paid for. A plan with amount 0 has no payments, so the next payment is
  the next real one. Both forms create one when the first payment they're given
  is not simply the next one on the schedule: from the change's date (or today,
  for a new subscription) until that payment. It shows in the history like any
  price change. During it, the monthly commitment is 0: the subscription costs
  nothing yet, and its upcoming price is shown next to it. Needed no format
  change. This fixed a bug where a next payment months away still counted the
  monthly payments before it.
- **Notes are part of the subscription**, plain text for now. Editing them records
  a revision like any other change, and they travel in backups and merge with the
  rest of the subscription. Line endings are normalised and trailing whitespace
  dropped, so the same text always compares equal.

### Estimated amounts, due dates and one-off changes (agreed 2026-11-04)

Designed together; built in steps. Each changes the stored subscription, so
the snapshot and backup format versions go up, and old files keep reading.

- **Estimated amounts.** A plan's `amount` is the amount expected per payment,
  as before; an optional `estimate` beside it says the amount isn't exact:
  a lower bound, an upper bound or both, and how the expected amount is
  chosen: the average of the bounds (needs both), the one bound given
  (the default when there is only one, and the form says so), or entered by
  hand (within the bounds). Later: estimated from past payments, falling
  back to the average or the hand-entered amount. Everything that adds up
  money uses the expected amount. Exact amounts store as before.
- **Totals with estimates** show the expected total, marked as including
  estimates, with a visible control to show the range as well: lowest to
  highest possible. A missing lower bound counts as 0; a missing upper bound
  leaves the range open ("or more").
- **Due dates.** A plan bills on its schedule; the payment can be due later,
  either a number of days after each bill or on a fixed day of the month (the
  first such day on or after the bill). By default it's due when billed.
  Payments, upcoming payments and monthly cash flow use the due date, when
  money actually leaves; plans and status changes apply by billing date.
- **One-off changes to a single payment.** For one scheduled payment, change
  its amount, its date, or both; recorded in the history and backed up, and
  later the source for estimates from past payments. A payment of 0 keeps its
  due date unless the user removes the payment entirely, which is optional.

### Reminders (agreed 2026-11-04)

- **What:** a payment due; a free trial ending; a bill, when it's billed on a
  different day from when it's due; a price change taking effect.
- **When:** one list of lead times for all subscriptions, by default a single
  reminder 1 day ahead, at a time of day (default 09:00, local). More lead
  times can be added (e.g. 3 days and 1 day). Per-subscription settings may
  come later.
- **How:** the core computes the coming reminders from the subscriptions and
  the settings, as a pure function. The app keeps the platform's schedule in
  step with it: at start-up and after every change it cancels the reminders
  it scheduled and schedules the coming ones (60 days ahead, at most 60), each
  with an ID derived from what it's about, so rescheduling never duplicates.
- **Android first**, with the official notification plugin: it fires while the
  phone dozes, and without exact-alarm permission falls back to inexact alarms
  (possibly some minutes late, fine for reminders; no special permission
  needed). Desktop shows notifications only immediately, so it gets no
  scheduled reminders yet; iOS follows when it can be tested.
- **Working around the plugin on Android** (2.8.0, found 2026-11-05): restoring
  after a reboot and cancelling depend on the notifications it saves, and three
  things stop that working. Its Rust API only offers `show`, which doesn't save;
  `batch` does, but saves a `sourceJson` field nothing fills in; and `cancel_all`
  sends null, which its Android side can't parse. So the app registers the
  plugin's Android class a second time under a small plugin of its own, for a
  handle that reaches `batch`, sends each notification's JSON as its
  `sourceJson`, and cancels with an empty object. It's a few lines against
  forking the plugin, but relies on its internals: after updating the plugin,
  check that reminders survive a reboot and that `just android-run` still
  schedules them. Failures are printed to the log (`Couldn't schedule
  reminders`).
- **Settings** are with the others: in the database and in backups (format
  version 5).

### Exchange rates
- **Rates are stored the way the ECB publishes them:** units of a currency per
  1 EUR, with the date the rate applies to and its source (ECB or manual). Other
  pairs are converted through EUR.
- **Choosing a rate for a date:** the latest one on or before that date. If there
  is none that old, the earliest one after it is used. Every conversion reports
  the rates it used, so the UI can show their dates.
- **A manual rate wins over an ECB rate for the same currency and date.**
- **An ECB rate is stale once it is more than 5 days old.** That covers the longest
  regular gap between ECB publications: Thursday to Tuesday over Easter. Manual
  rates are always shown as manual, never as fresh or stale.
- **Fetching** (2026-11-03): the ECB Data API's daily rates against the euro, as
  CSV with `detail=dataonly` (eight plain columns, parsed in `crates/core/src/ecb.rs`
  without a CSV library). The first fetch takes two weeks; later ones start the
  day after the newest cached rate, never after today (the API rejects future
  start dates), and not again within an hour of a fetch that brought new rates.
  A background task checks at start-up and then every hour while the app runs,
  and tells the UI when it stored new rates (the `rates-updated` event).
  Failing (offline) is silent except that out-of-date rates are flagged.
- **HTTP: `reqwest` with rustls** (its default TLS). It verifies certificates with
  each platform's trust store (`rustls-platform-verifier`), and Tauri already
  locks the same `reqwest` version. **Except on Android**, where the platform
  verifier panics unless it is initialised from Java (a Gradle dependency plus
  JNI setup): there, the app trusts Mozilla's root certificates
  (`webpki-root-certs`, from the rustls project) instead. Their list updates
  with the app.
- **Rates are stored in `exchange_rates`**, keyed by currency, date and source,
  with the rate as exact decimal text. ECB rates are a cache; manual rates are the
  user's data, so they are in backups (format version 3).
- **Totals refuse to guess**: if any currency involved has no rate at all, the
  converted total isn't shown, and the missing currencies are named.
- **The reporting currency is the default for totals**; the dashboard can show
  them in any other currency without changing it, or make that the default.

## Data history

- **Every subscription change is logged forever.** Each change (create, edit, price
  change, status change, delete, import) appends a revision: a full copy of the
  subscription, with when, on which device and why. Deleting a subscription keeps
  its history.
- **History works like a Git repository with a single branch.** Revisions have
  UUIDs, never auto-increment integers, so revisions made on different devices
  can't collide. Each names the revision it replaces (its parent); a revision that
  settles a conflict names both sides. Revisions are never rewritten: undoing a
  change appends a new one.
- **A subscription's latest revision is the one no other revision replaces**, not
  the newest by ID or by time, which device clocks can't be trusted for.
- **Importing a backup and, later, syncing devices are the same operation**:
  merging one history into another (see "Backups").
- **Restoring a version appends it as a new revision** on top of the current one
  (cause "edited", or "created" for a deleted subscription), so restoring can
  itself be undone. Deleted subscriptions are listed on their own screen and
  restored the same way.
- **The history view compares each revision with its first parent**: for a
  revision that settled a conflict, that is this device's side.

### Future direction: syncing devices (not built yet)

Backups already carry the whole history and imports merge it, which is what
syncing needs. What's missing is moving the history between devices
automatically.

- **Under consideration: syncing through storage the user already has** (Nextcloud,
  iCloud Drive, Google Drive). If we do this, the
  SQLite database must never sit in the synced folder: file-sync tools copy whole
  files without locking, and two devices writing to one database corrupt it or
  leave "conflicted copy" files. What would sync is the history: each device
  writes its new revisions as files to a shared folder and merges in the other
  devices' files, the same way an import does.

## Backups

- **A backup holds the whole change history and the settings**, as JSON. There is
  no separate list of current subscriptions: the current state is each
  subscription's latest revision, so the file can't contradict itself. Including
  the history from the first version avoids supporting a second, history-less
  format forever, and it is what lets imports tell outdated copies from conflicts.
- **Format**: `{"format": "epicycle-backup", "version": 1, "exported_at",
  "device_id", "settings", "revisions": [...]}`. Revisions are written parents
  first. Amounts are integer minor units, dates ISO 8601, timestamps RFC 3339.
  `crates/core/testdata/` has a sample of each version; tests check that every
  one still imports, and that the latest exports unchanged.
- **Old versions are temporary while the format is young.** Each new version
  still reads the older ones for now; once the format settles, the oldest can be
  dropped (2026-11-03, the user's call).
- **Version 3** (2026-11-03) adds `settings.favorite_currencies` and
  `manual_rates`, the exchange rates the user entered (ECB rates are re-fetched,
  not backed up). Older files read as having neither.
  - Merge adds the backup's manual rates; where both sides have one for the
    same currency and day, this device's stays. Favourites stay as they are,
    like other settings.
  - Replace takes the backup's rate where both have one, keeps this device's
    others (it loses nothing), and takes the backup's settings, favourites
    included.
  - Replacing the history leaves exactly the backup's manual rates and settings.
- **Version 2** (2026-11-03) adds `notes` to subscriptions, left out when empty.
  Version 1 files are read as version 2 files without notes. The version went up
  even though nothing else changed, so that older apps refuse these files rather
  than silently dropping the notes.
- **Versioning**: `version` covers the whole file and goes up on any change to
  the format. The app reads every older version and refuses newer ones with a
  message to update the app.
- **Validation comes first.** The whole file is checked before the database is
  touched: format and version, every subscription (the same rules as the app's own
  data), each revision's subscription ID matching its contents, every parent
  present in the file, no cycles, one latest revision per subscription, and no
  revision ID that the device has with different contents. The import itself is
  one transaction: all of it applies or none of it does. Before importing, the app
  shows what the import will do.
- **Merge import compares histories, subscription by subscription.** This
  replaces the earlier plan of "the later `updated_at` wins", which brought deleted
  subscriptions back when an old backup was imported, and let a device with a
  wrong clock overwrite newer edits.
  - Same latest revision on both sides: nothing to do.
  - The backup's version is an older point in this device's history: keep this
    device's. In particular, deleted subscriptions stay deleted.
  - This device's version is an older point in the backup's history: take the
    backup's.
  - Both changed it separately (a conflict): the later change wins and a tie keeps
    this device's. A new revision with both sides as parents records the result,
    so the other version stays in the history and can be restored. The import
    summary lists each conflict and which side was kept. Identical separate
    changes are joined the same way but not reported as conflicts.
  - Subscriptions only on this device are kept; only in the backup, added.
  - Settings stay as they are on this device.
- **Replace import makes this device match the backup, but erases nothing.** This
  replaces the earlier plan of saving a copy of the database first: the history
  already keeps everything, which matches "keep data forever".
  - Subscriptions only on this device get a deletion revision.
  - Subscriptions where this device differs get a new revision with the backup's
    version, on top of this device's history (with both parents if they diverged).
  - Settings come from the backup.
  - Anything replaced can be restored from its history.
- **"Replace everything, including history" is the one exception to keeping
  data forever** (2026-11-03, at the user's request). It makes this device's
  history exactly the backup's: revisions only on this device are permanently
  deleted. The preview counts them, and the confirmation is a modal with a red
  button that stays disabled for 5 seconds (a ring counts down) next to a
  prominent Cancel. Plain Replace stays the non-destructive choice.

## Storage

- **The current state is stored in normalised tables** (`subscriptions`, `plans`,
  `status_changes`) with `CHECK` constraints, so SQLite rejects invalid rows, and
  the compile-time checked queries have real columns to check.
- **History is the append-only `revisions` table.** Each revision holds a full JSON
  copy of the subscription, tagged with a format version so old copies can be
  upgraded when the format changes. A deletion is a revision with no copy.
- **Revision IDs are UUIDv7**, so they sort roughly by creation time. Parent
  links, not IDs or `created_at`, define the order of a history.
- **A revision with two parents** stores the second in `merge_parent_id`: two
  columns rather than a separate parents table, since there are never more than
  two.
- **Saving a subscription that didn't change records no revision.**
- **Snapshot version 2** adds notes, left out of the JSON when empty, so
  version 1 snapshots read unchanged and need no upgrade. Leaving empty notes out
  also keeps old and new snapshots of the same subscription byte-identical, which
  the "no change, no revision" check relies on.
- **Builds use the committed query metadata in `.sqlx/` and need no database.**
  After changing a query or a migration, run `just sqlx-prepare`
  and commit the result. CI runs it with `--check`.
